17:31 Slice 4, Entry, Account and Ledger. Account is an id plus its opening balance, so the closing balance is a fold that starts from the opening balance and adds every entry with value date on or before the day. No zero factory and no account lookup needed. Amounts are signed, a debit is negative, so the balance is a plain sum. I asked for the posting day on Entry from the start because the brief gives it for every event. It never affects a balance. The ledger refuses a posting day earlier than the last one: value dates can go back, posting days cannot. That also means the brief's listed order, E9 then E10, would be refused if followed literally. Entry refuses an amount in the wrong currency before it can be appended, since an append-only ledger cannot remove a mistake. Eight tests written by Claude Code, including C1 at ledger level: Day 2 reads -370.00 once E7 is posted. From this slice on I run the build and tests myself.

17:50 Slice 5, events, outcomes and the replay loop, credits and debits only. Event is a sealed type with one record per kind, so the replay's switch will not compile if a later kind is added and not handled. Event amounts are positive as the brief writes them, the kind gives the direction, and the replay negates a debit. The loop walks Day 1 to the last day and picks that day's events in listed order, so no sorting. I asked whether this drops E10: it does not, E10 is picked up on Day 5 after E7 and E8, ahead of E9 on Day 6. A stream with a posting day outside the window is refused before anything is posted, because the loop would otherwise never reach that event and lose it silently. Outcomes go to an append-only log, POSTED is the only status so far. Money gained negate and isPositive. Nine new tests written by Claude Code. Added the replay order section to AMBIGUITIES.md. I then noticed that within each account the listed order already runs by posting day, and only E10 against E9 across accounts is out of sequence. Rewrote the section around the real reason, the day close being one event for the whole ledger, and added that order within a day matters once: E7 before E8 is why Auth-B is declined.

18:10 Slice 6, authorisations, holds and available balance. No hold list. Available balance is today's ledger balance less those holds, and an authorisation is declined if the hold would take it below zero. Exactly zero is approved. An approved hold posts no entry. The authorisation record keeps the brief's value date although nothing reads it, because an event is the record of what arrived. A decline carries no reason text. That comes with E6 in the settlement slice. I left the real E8 figure of -155.00 for later, since Day 5 needs the settlement first. Money gained isNegative. Eight new tests written by Claude Code.

An accepted settlement posts a debit for the settled amount with its own value date. The hold is released by the SETTLED outcome appearing in the log, so there is still no hold list. No cap against the hold and no balance check, as AMBIGUITIES.md already says. Outcome gained a reason text, empty unless rejected. 18:56 Slice 11, reversal. The Reversal event carries no amount, as in the brief, so the compensating entry takes the target's amount with the opposite sign and cannot reverse a different figure. Unknown events, authorisations, a second reversal and a wrong account are all rejected with no movement. I allowed credits as well as debits.
